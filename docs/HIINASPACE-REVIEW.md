# hiinaspace repository review for FPSloppa

Reviewed 2026-09-12 against the current workspace: Godot 4.7.2, Vulkan Mobile, OpenXR on SteamVR/WiVRn and standalone Android, VRM/MToon avatars, TwoVoIP voice, Steam Audio, and a stripped console server. The review covers the public repository inventory, ten Godot-related project READMEs, selected implementation/build files and the engine fork. This is a source review; third-party binaries were not built or loaded. Upstream test results below are the author's reports, not new FPSloppa measurements.

My recommendation is to evaluate material import and audio separately, reuse pose-validation ideas, and retain the existing runtime systems until comparisons demonstrate a benefit.

| Repository | Potential use | Assessment |
|---|---|---|
| [liltoon-godot](https://github.com/hiinaspace/liltoon-godot) | Better preservation of Unity/VRChat avatar materials | Best bounded converter improvement; alpha, MIT. Matches our Godot/Mobile renderer. |
| [godot-network-audio](https://github.com/hiinaspace/godot-network-audio) | Voice resilience under jitter, loss and frame stalls | Strong experimental candidate; not a production replacement yet. |
| [godot-vr-humanoid-pose](https://github.com/hiinaspace/godot-vr-humanoid-pose) | Tracker capture, dropout simulation and quantitative IK comparisons | Useful research/testing tools now; runtime replacement is premature. MIT. |
| [godot-renik](https://github.com/hiinaspace/godot-renik) | Alternative spine, limb, hip and foot-placement solver | Viable optional solver benchmark. MIT; native builds and avatar adaptation required. |
| [godot_planar_reflection](https://github.com/hiinaspace/godot_planar_reflection) | A perspective-correct stereo lobby mirror; rendered portals | Viable optional client feature. MIT. Start with frustum mode on stock Godot. |
| [godot-libmpv-zero](https://github.com/hiinaspace/godot-libmpv-zero) | In-world video screen or prerecorded spectator video | Defer: experimental patched dependencies and substantial packaging cost for a secondary feature. |
| [godot_mpv](https://github.com/hiinaspace/godot_mpv) | Older libmpv video integration | Lower priority fork; its Godot 4.4 EGL/GLES-based integration is a less direct match for our Vulkan/XR path. |
| [godot-openvr-overlay](https://github.com/hiinaspace/godot-openvr-overlay) | Separate SteamVR diagnostic overlay | Unsuitable as the main game XR/tracker backend. Windows/OpenVR overlay scope excludes the usual WiVRn path. |
| [mainspring](https://github.com/hiinaspace/mainspring) | RenIK integration and physical interaction examples | Reference project, not a subsystem to transplant. Code licence does not automatically cover all included avatar/audio assets. |
| [vr-has-reclined](https://github.com/hiinaspace/vr-has-reclined) | Seated/reclined interaction examples | Low benefit: older Godot 4.2 jam project, with an explicit code-quality caveat. FPSloppa already has seated controls. |
| [godot engine fork](https://github.com/hiinaspace/godot) | Specific mirror/video engine patches | Examine individual patches only when needed; changing the game engine creates another Linux/Windows/Android export maintenance obligation. |

**Avatar materials.** liltoon-godot supports shadow bands, rim light, MatCap, normal maps, alpha modes and an outline pass. Its Unity `.mat` importer resolves texture GUIDs through `.meta` files, but does not reconstruct complete prefabs or renderer assignments. Many advanced features remain absent, including emission and second/third base textures. Those limits are documented in its [compatibility matrix](https://github.com/hiinaspace/liltoon-godot/blob/master/docs/compatibility.md).

Our independent AvatarConverter currently warns that Unity shaders and prefab edits are not imported (`external-tools/AvatarConverter/app/converter.gd`). My proposed first step is to adapt material classification and supported property extraction there. The output remains VRM: a Godot ShaderMaterial cannot simply be embedded as a portable VRM material. Convert supported values to MToon or an explicit approximation. A game-side lilToon shader path would need separate material metadata, import handling and Android profiling. Do not package the upstream demonstration avatars merely to obtain the addon.

**Network audio.** Its author reports synthetic transport scaling to 32 participants and a seven-source spatial Godot harness, with roughly 16 participants as the target. Opus plus Rust NetEq are a plausible improvement to jitter/loss handling; the API is experimental and there are no packaged builds. [Current README](https://github.com/hiinaspace/godot-network-audio/blob/master/README.md).

The [Cargo manifest](https://github.com/hiinaspace/godot-network-audio/blob/master/Cargo.toml) requires Godot API 4.7 and experimental threading, although the [extension descriptor](https://github.com/hiinaspace/godot-network-audio/blob/master/addons/godot_network_audio/godot_network_audio.gdextension) still says 4.1. Its library entries omit Android. The root licence is WTFPL while workspace metadata declares MIT OR Apache-2.0; resolve the notice discrepancy before redistribution. The optional Iroh transport is not required for codec experimentation.

My suggested integration retains FPSloppa's authenticated server relay, proximity/team routing, mute/PTT settings, radio effects and mouth activity. Keep decoding on clients, with a selectable backend and explicit packet-format compatibility. Threaded encoding alone will not remove ENet/main-thread delivery stalls: the [sender](https://github.com/hiinaspace/godot-network-audio/blob/master/gdext/src/sender.rs) normally drains packets in `process`, and exposes a separate worker callback path. Compare loss/reordering, 16 active speakers, microphone switching, repeated reconnects, loading stalls and Android CPU/latency before adopting it.

**Pose estimation and RenIK.** The pose project is primarily a Python estimator and validation harness. Its Godot [SkeletonModifier implementation](https://github.com/hiinaspace/godot-vr-humanoid-pose/blob/main/godot/addons/godot_vr_humanoid_pose/scripts/vr_humanoid_pose_modifier.gd) still has no bone-application implementation. The [live harness](https://github.com/hiinaspace/godot-vr-humanoid-pose/blob/main/godot/README.md) sends tracking to a Python sidecar; its OpenVR overlay input needs adaptation to use our OpenXR/WiVRn poses. Capture/replay, tracker-loss tests, foot slip and knee/torso stability measurements are the useful immediate parts. Its stated 75–80 ms pose-latency budget is a research target, not a measured result or a suitable default for weapon/hand latency.

RenIK is the more concrete runtime alternative. Its [build workflow](https://github.com/hiinaspace/godot-renik/blob/main/.github/workflows/runner.yml) includes desktop and Android architectures, but that does not establish compatibility or speed in FPSloppa. Compare it behind an optional avatar solver, using identical recorded inputs. Preserve our tracker overrides, calibrated proportions, crouch/prone gait, local spring-bone limits and authoritative collision. An IK replacement does not itself fix missing trackers or transport latency.

**Mirror and video.** Our lobby mirror is currently a 512×768, 30 Hz, isolated avatar preview, not a reflection of the room. The planar addon could supply stereo perspective, but uses two viewports. Its [implementation](https://github.com/hiinaspace/godot_planar_reflection/blob/main/mirror.gd) scales their resolution from the XR render target; add strict resolution/visibility limits and profile Android. Screenspace mode needs `override_projection`; the frustum branch also sets that property, so guard the optional property on stock builds. A rendered portal would still need our teleport/collision/telefrag logic separately.

The newer mpv project reports Linux playback and initial VR testing, but requires matching patched Godot, mpv/libplacebo and Steam Audio dependencies; current portable packaging and Windows revalidation remain unfinished. See [current Linux instructions](https://github.com/hiinaspace/godot-libmpv-zero/blob/main/LINUX.md). It plays media rather than FPSloppa demo state, so it would not improve demo simulation or camera editing by itself. Its Unlicense wrapper also does not replace the dependency-specific licensing obligations.

Suggested order: material-import prototype; audio backend comparison; pose-validation tooling and optional RenIK comparison; then an optional stereo mirror. Defer video playback and external overlays until there is a concrete game feature requiring them. No addon or engine change was made during this review.
