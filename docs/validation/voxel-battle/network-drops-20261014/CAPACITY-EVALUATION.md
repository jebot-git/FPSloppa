# Remaining 64-player blockers and server architecture options

Evaluation: October 14, 2026. This assessment uses the final fixed-default VPS profile, source inspection and existing native differential results. It does not claim newly measured optimization gains or authorize a rewrite/deployment. [Computed figures](capacity-evaluation.json), [raw profile](raw/default-fixed/64/report.json), [connection investigation](REPORT.md), [native results](../native-backend-20261013/REPORT.md).

## Current status and required gain

64 independent clients now complete the 155-second test, with all 64 retained throughout the two-minute profile. Connection capacity is established for this cached-asset loopback workload. Sustainable simulation capacity is not.

The authority achieved 21.07 Hz against a 30-Hz target: 47.46 ms average wall interval versus a 33.33-ms budget. Reaching 30 Hz requires at least **42.4% more throughput / 29.8% less wall time per tick**. This only closes the average gap; it leaves no combat or scheduling reserve. A planning target of 25 ms average would require about 47% less work. The stronger release gate is p95 full tick work <=25 ms and p99 <=33.33 ms, not merely that average. The current callback p95 of 67.99 ms would need about 63% reduction to meet 25 ms; that comparison is a target gap, not a measured reducible fraction.

| Measured category | Median ms | p95 ms | p99 ms | Meaning |
|---|---:|---:|---:|---|
| Simulation `_server_tick` | 29.88 | 49.49 | 58.50 | Includes class services, player simulation, hits/projectiles and objectives |
| Whole authority physics callback | 41.35 | 67.99 | 84.81 | Includes extra network polling, simulation, history and due snapshots |
| Snapshot preparation/submission | 5.96 | 8.28 | 10.80 | Per snapshot event, not every simulation tick |
| Snapshot transport/fanout | 4.00 | 10.85 | 13.41 | Per completed snapshot event, main thread |
| Encoder worker | 1.66 | 2.74 | 3.38 | Already off the authority thread; not an additive main-thread cost |
| Projectile update | 0.005 | 11.29 | 14.45 | Included in simulation; sparse median hides active-projectile spikes |
| History recording | 0.366 | 0.513 | 0.581 | Already native-backed; small opportunity |

These are overlapping distributions. Do not add percentile cells, subtract the engine monitor from callback percentiles or treat their differences as measured exclusive costs. The engine physics monitor can include catch-up/batching effects and is not proof that collision alone costs its reported 55.73-ms median.

Central-window process sampling, excluding the first/last 20 seconds of candidate lifetime, gives **99.8% of one vCPU on the main thread**, **107.8% across all server threads**, and approximately **92.6% of server CPU work on the main thread**. Peak sampled authority RSS is about **496 MiB**. This window is an approximation, not an exact tick-aligned profile. The 64 client processes and the live production server also consume host CPU and are excluded from these authority figures. No current CPU-steal/host-scheduling attribution was captured.

The 12-vCPU/24-GB target therefore has available aggregate CPU and ample measured authority memory; the critical path is serial. More encoder workers, more RAM, GPU optimizations or further avatar simplification do not address this observed headless workload. The small range-filter batch was already faster serial than on workers in the earlier native test.

## Blockers still present

1. **Serial simulation and its tail latency.** Simulation p95 alone exceeds the full tick budget. Native codec/hit/history improvements have not moved CharacterBody movement, live world queries and gameplay orchestration out of the serial path. AI was disabled in this run, so bot logic cannot explain the remaining baseline deficit.
2. **Expensive ticks are not yet attributed precisely.** The current live profiler does not separate CS math, stair queries, slide/snap, room-scale collision, class tools, spotting LOS, input validation/dispatch and damage/impact commits. Movement/world queries are a strong source-level candidate, not yet a measured exclusive winner. Older rendered VRM/weapon-impact profiles concern different workloads and cannot fill this gap.
3. **Transport has reserve problems even though peers survive.** The final socket counted 26,951 dropped datagrams, including the connection burst and subsequent traffic. Physics-step polling prevents prolonged starvation; a 425,984-byte effective receive buffer does not establish loss-free WAN operation. The 4-MiB request was kernel-clamped. Increasing the permitted buffer is a burst safeguard, not a remedy for CPU throughput.
4. **Simulation-clock slowdown reduces delivered updates.** The nominal 20-Hz snapshot accumulator produced about 14.05 batches per wall second at 21.07-Hz simulation. Simulation-based cooldowns and timers likewise progress more slowly under this overload. Stable connections should not conceal degraded gameplay cadence.
5. **The workload understates a real full battle.** Synthetic clients send poses and initial firing but do not execute physical magazine-reload gestures. The `reload` input exists, but VR players take the gesture-based reload path; reserve refill does not make firing continuous. Dense CQ combat, multiple tanks, simultaneous turrets/healing fields/airstrikes, actual voice and asset bursts have not passed a 64-player acceptance test. Bots are a separate additional load.
6. **Production has not received the candidate.** The stable production service still runs the earlier 32-slot release. Candidate results require a tested deployment and rollback before they describe the live service.

## Ranked performance opportunities

| Priority / approach | Potential and evidence | Cost / limitation |
|---|---|---|
| 1. Profile and reduce repeated movement/world queries | Largest likely baseline opportunity inside the ~30-ms median simulation category. Grounded CS movement performs an edge ray, step-test and slide/snap; failed step cases can perform several additional sweeps. Room-scale movement is invoked even for a zero request. Count/time these first; skip genuinely unnecessary queries and reuse scratch objects/results within valid boundaries. | Low to medium effort for fast paths; no measured savings yet. Must preserve stairs, slopes, recovery, prone/crouch clearance, jetpack, physical movement and player contacts. A C++ wrapper cannot remove engine query cost by itself. |
| 2. Batched native player/class simulation with persistent typed state | Removes remaining per-player script dispatch, Dictionary traversal/copies and temporary allocations; enters native code once per batch. The existing direct native hit kernel was ~14.6x faster, but that is a kernel result, not a forecast for movement. | Medium/high effort. Start serial to isolate language/data savings. Retaining live Godot collision limits parallelism. Measure marshal/commit time so work is not simply moved into conversions. |
| 3. Interest-based replication and narrower state | Current snapshots include all actors, all XR poses, ammo/owned weapons, class/magazine state and mode records, then broadcast every encoded packet to all admitted peers. Global encoding is shared, but fanout/payload scales toward N squared. Recipient groups, high-rate nearby actors, low-rate distant actors, owner-only acknowledgements/inventory and event-driven stable fields can reduce main-thread fanout, allocation, packet rate and bandwidth together. | Medium/high effort. Per-peer cache/membership and visibility transitions need baseline/keyframe handling. Preserve recon/designation markers, long-range scopes/projectiles, vehicle combat and team state. Do not treat spotting radius as a universal render/replication cutoff. Dense 64-player combat gives less culling benefit. |
| 4. Stagger periodic LOS/class work and share spatial indices | Spotting performs its 10-Hz scan together; turrets and other class services add queries. A shared actor/vehicle grid plus bounded, staggered scans can reduce duplicate range work and p95 spikes. Batch projectile/cover/damage queries against frozen state where semantics permit. | Medium effort. Preserve existing maximum detection delay, same-tick hit ordering and life/map tags; staggering must not silently add a scan period. The small native range math itself is already cheap. |
| 5. Native collision/controller phase over an immutable world | Highest opportunity to use several CPUs for the dominant path. Export static terrain/building/tree collision into a query representation, freeze dynamic actors/vehicles per phase, batch locomotion and rays/sweeps, then commit ordered results. Can remain inside a Godot extension. | High effort. Terrain-only height sampling cannot replace building walls, caves/overhang geometry, thin cover, capsule sweeps, stairs, movers or dynamic contacts. Requires a full collision/prediction parity suite. |
| 6. Physics backend/settings and collision layout experiments | Verify the template's effective backend, then compare explicit Godot Physics/Jolt, supported physics threading, grouped static collision and cached query objects. Potentially valuable if collision dominates. | Moderate experiment cost, benefit unknown. New projects using Jolt does not prove this template's DEFAULT resolves to it. Settings alone do not parallelize script-driven movement loops. Avoid collision simplification that changes cover/access. |
| 7. Dedicated network service / native packet batching | An independently serviced native ENet host and bounded input/output queues can protect ACK processing, coalesce replaceable pose/movement updates and reduce thousands of RPC dispatches. Use one transport owner; route immutable accepted commands to simulation in order. | Medium/high effort. Fire/jump/reload events cannot be discarded with replaceable poses. Off-thread use of the current live multiplayer tree is not acceptable. Standalone/custom transport requires client integration and protocol work. |

The received snapshot payload was approximately **81.2 Mbps aggregate**, averaging each client's bytes over its own 155-second lifetime, and roughly **9,544 packet deliveries/sec**. This excludes ENet/UDP/IP overhead, retransmits, voice, assets and other RPCs. It is below a nominal 1-Gbps link but creates meaningful per-packet CPU work. The shared asset bucket refills at 4 MiB/s and charges gameplay reservations first; this much global gameplay fanout can leave asset transfers without tokens. Separate protected asset capacity or reserved scheduling is needed, alongside reduced replication. Increasing asset priority must not starve gameplay.

Useful numerical bounds, not promises: eliminating the encoder's ~1.66-ms median work cannot remove ~1.66 ms from the main-thread critical path because it is asynchronous already. Eliminating history removes only a small fraction of a tick. Snapshot preparation/fanout have about 6/4 ms median per event of directly addressable work, but neither runs every tick, both must retain essential work, and their joint tail reduction cannot be inferred by adding p95 cells. Halving recipient fanout approximately halves fanout-dependent bytes/calls for the same records; it does not halve simulation or shared encoding. Cutting a dominant simulation phase in half could be far more valuable, but its exclusive time must first be measured.

Godot's active scene tree is not thread-safe; enabling physics-server threading does not license arbitrary CharacterBody calls from workers. Keep synchronized live queries in their supported phase or move them to an explicitly owned collision world. [Godot threading](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html), [query synchronization](https://docs.godotengine.org/en/4.7/tutorials/physics/ray-casting.html).

## Complete rewrite versus incremental native authority

**A straight C++ translation inside Godot:** lower allocation/interpreter overhead, existing client/protocol and content pipeline retained. Lowest migration risk of the native options, but CharacterBody/world queries and RPC fanout can stay serial. It may close part of the gap; there is no evidence that translation alone guarantees 64-player combat at 30 Hz.

**A native authoritative world inside Godot:** persistent contiguous player/projectile/vehicle state, exported collision, batched controllers/queries, staged main-thread commit and frozen replication. Godot can remain the admission/RPC/asset/profile host. This addresses the architectural bottleneck while retaining the existing transport adapter and client. Recommended next large step if measured query cost prevents targeted fixes from reaching the gate. It is also a migration path toward a standalone server.

**A standalone C++ server:** greatest control and long-term ceiling. Fixed-step scheduler; one network I/O owner; bounded per-peer input queues; typed simulation; 2–4 coarse simulation/query workers initially; stable damage/objective/vehicle commits; asynchronous recipient-group snapshots; separate disk/profile/asset workers. Static map collision is prebuilt offline and versioned with the map manifest. Clients still render the existing jungle/UT99 content. No face/IK/animation rendering is needed server-side beyond authoritative pose validation and hit geometry.

A standalone server must port the full gameplay contract: CS/optional Quake movement, posture/room-scale/jetpack, lag compensation, tracked weapon reach, magazines/gestures, all weapons/ordnance and class utilities, CQ scoring/progression, tanks/terrain road/water rules, revival, reconnect/life/epoch rules, skin recognition/hash/distribution, voice/radio routing, administration and persistence. Retain differential input replay against the existing authority. Client prediction needs a compatible controller, potentially a shared native controller library.

ENet alone is not the existing Godot RPC protocol. Node paths/RPC declarations/signature negotiation and Variant payload semantics need an adapter or replacement. Initially keep a thin Godot gateway, or introduce a versioned client/server binary protocol and migrate both ends; do not promise an unmodified Godot client will connect to a bare ENet rewrite. The high-level API is scene-tree/RPC based and Godot uses a modified ENet implementation. [Godot networking contract](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html).

Direct Jolt is a viable native collision candidate, not a measured winner here. Its CharacterVirtual supports concurrent updates and explicit character/character collision handling, but query inclusion, interaction order, sensors and moving platforms require deliberate handling. Implement CS acceleration/recovery/posture semantics around it rather than assuming its defaults match current play. [Jolt controller architecture](https://jrouwe.github.io/JoltPhysics/), [Godot integration differences](https://docs.godotengine.org/en/4.7/tutorials/physics/using_jolt_physics.html).

Rewriting only networking cannot remove the measured simulation p95 deficit. Removing Godot entirely is useful only if it also removes the expensive execution/data/collision architecture. A single typed native authority is preferable to legacy district subservers for this unified map. Partitioning the map across processes introduces ownership, cross-border projectiles/damage, transfers and replication; 64-player dense combat can concentrate in one partition anyway.

## Quantifying the rewrite ceiling honestly

There is no measured whole-server rewrite speedup yet. Use benchmark requirements and conditional scaling instead of promising 2x/4x:

- 1.42x current throughput merely reaches 30 Hz average.
- 1.90x reduces the present average interval to approximately 25 ms; percentile and full-combat gates still need measurement.
- 3x would give approximately 15.8 ms average in the same workload, a useful headroom goal rather than a forecast.
- If 50% of total work were parallelizable on four equally effective workers, ideal Amdahl speedup is 1.60x; if 70%, 2.11x. Scheduling, shared world-query locks and virtual-core contention lower these bounds. The measured 92.6% main-thread share is not the parallelizable fraction.

A complete rewrite has the largest ceiling, highest parity/deployment risk and highest implementation cost. The strongest benefit comes from fewer queries, contiguous native state, coarse parallel query/controller batches and reduced recipient work together. None requires discarding the Godot client or the map authoring tools.

## Recommended decision sequence

1. Instrument exclusive phases and query counts: input unpack/validation/apply, CS math, step/slide/snap/room-scale collision, world ray/shape queries, spotting, class tools, projectile candidates versus cover/impact commits, snapshot state construction/local apply/deep copy, encoding, RPC fanout and network poll. Record mean/total and tick correlation as well as percentiles. Add tick deadlines/lateness and wall-clock input/snapshot age. Input counters are empty at the current normal log level; collect reliable accepted/rejected/rate data independently of verbose logging.
2. Move load generators off-host; repeat the same seed/commands at 32 and 64, clustered and dispersed. Capture CPU steal/scheduling and compare explicit physics backends only after identifying the current template's backend. This isolates VPS contention and actual world-query cost.
3. Implement verified no-work fast paths, shared/staggered candidate work, owner-only/state-cadence replication and recipient groups. Compare default/fallback paths with identical replay; retain transport polling and inspect socket drops.
4. Build a single batched native movement/controller prototype. Compare serial native against reference, then 2/4 workers using a supported query world. If collision dominates, prioritize this over additional codec micro-optimizations. Promote it into a native authority module if parity and throughput justify it.
5. Consider standalone hosting after that module can reproduce gameplay and clear the budget. Keeping a thin gateway initially makes migration reviewable and lets the native simulation evolve without rewriting every client RPC at once.
6. Acceptance: >=15 minutes with 64 off-host clients after admission, stable 30-Hz wall-clock simulation, p95 complete tick work <=25 ms and p99 <=33.33 ms, bounded lateness/input/snapshot queues, no server-induced disconnects and no ongoing baseline RX overflow. Exercise actual reloads/continuous combat, CQ, all utilities, occupied tanks, physical motion, radio/voice, join/reconnect/skin transfer. Validate delivered client state, not just server send counters. Run bots as a separate capacity class.

Recommendation: pursue the batched native authority and replication changes before committing to a standalone rewrite. They attack the same high-value work, retain already-tested gameplay, and produce reusable components if a full rewrite remains necessary. Do not declare 64 supported on connection survival alone or increase worker count without a measurable parallel workload.
