# Static rendering study — 12 September 2026

Decision update, 13 September 2026: recommendations 10 and 11 were tested and declined after visual review; see the [closed evaluation](STATIC-RENDERING-CANDIDATES-1011.md). Recommendations 12–14 will remain unexplored. The original study below is retained as historical context.

The best next improvements for FPSloppa are calibrated lightmap colour response, targeted bake/art refinement, map-specific skies and restrained fog, and inexpensive animated surface textures. Preserve Mobile/Vulkan, mipmapping and the existing single-pass baked surface path. Directional lightmaps and static reflections are plausible second-stage experiments; blanket normal mapping, parallax and screen-space effects offer weaker value for standalone VR.

This is a source-code/documentation study and review of existing FPSloppa Vulkan captures, not a benchmark of the three ports or a new Quest/Pico test. Runtime light sources, shadow maps, realtime GI, animated lighting and avatar/MToon changes are excluded. Animated texture coordinates and view-dependent sampling of **offline** reflection maps are included: neither requires runtime lighting or scene capture. No production renderer changes were made.

## What the ports actually provide

| Port | Relevant rendering, excluding realtime lighting | Comparison with FPSloppa |
| --- | --- | --- |
| QuakeSpasm | Its world shader multiplies colour by a lightmap, applies overbright scaling, adds fullbright pixels, then fog. It supports mipmapping/anisotropy, transparent-edge cleanup, animated textures and water. | Closest reference for a restrained Quake appearance. FPSloppa already has colour/lightmap/glow sampling and anisotropic mips. Its lighting response differs substantially; generic BSP liquid/texture animation and authored sky/fog handling are gaps. |
| Zandronum | The examined hardware renderer uses sector light levels, coloured lighting/fog and selectable Doom-style distance attenuation. Brightmaps keep selected texture regions bright; warp shaders animate UVs. | Useful references for room colour separation and surface animation. Sector lighting is not a replacement for FPSloppa's finer spatial lightmaps. Zandronum is not current GZDoom: do not attribute modern GZDoom-only features to it. |
| DarkPlaces | Separate shader modes support ordinary lightmaps, directional/deluxe lightmaps, normal/gloss maps and cubemap reflection masks. Its documented asset conventions include normal, bump and glow companions. | Static directional shading is technically possible without realtime lights. It needs direction data and authored companion textures that FPSloppa currently lacks. Expensive offset/relief and reflection/refraction paths are optional features, not prerequisites for its basic appearance. |

Primary code reviewed: [QuakeSpasm world shader](https://github.com/sezero/quakespasm/blob/f5fe17864918239d443fe4c0d6bfb980e44d19e6/Quake/r_world.c), [texture handling](https://github.com/sezero/quakespasm/blob/f5fe17864918239d443fe4c0d6bfb980e44d19e6/Quake/gl_texmgr.c), [fog](https://github.com/sezero/quakespasm/blob/f5fe17864918239d443fe4c0d6bfb980e44d19e6/Quake/gl_fog.c); [Zandronum light/fog management](https://github.com/TorrSamaho/zandronum/blob/bdd0f7beb43d9786cc13502395f60aa84d34e28d/src/gl/renderer/gl_lightdata.cpp), [main shader](https://github.com/TorrSamaho/zandronum/blob/bdd0f7beb43d9786cc13502395f60aa84d34e28d/wadsrc/static/shaders/glsl/main.fp), [brightmap](https://github.com/TorrSamaho/zandronum/blob/bdd0f7beb43d9786cc13502395f60aa84d34e28d/wadsrc/static/shaders/glsl/func_brightmap.fp), [UV warp](https://github.com/TorrSamaho/zandronum/blob/bdd0f7beb43d9786cc13502395f60aa84d34e28d/wadsrc/static/shaders/glsl/func_warp1.fp); [DarkPlaces shader modes](https://github.com/DarkPlacesEngine/darkplaces/blob/5d80f03e26871b273da103f3b750820a3718c01a/shader_glsl.h) and [asset documentation](https://github.com/DarkPlacesEngine/darkplaces/blob/5d80f03e26871b273da103f3b750820a3718c01a/darkplaces.txt). ## FPSloppa baseline

The installed editor reports Godot 4.7.2. `project.godot` selects Mobile/Vulkan with OpenGL fallback disabled. Android defaults to 2× MSAA; desktop to 4×. Dynamic foveation is requested, but that setting alone does not prove every device activates it. `arena.tscn` uses Filmic tonemapping, a shared procedural sky, and disabled bloom/SSAO.

All 25 bundled maps have RGB lightmaps containing the tested low AO; the bake workflow also uses supersampling and one bounce. The material audit found 543 baked materials and 27 with glow, out of 560 materials. Ordinary baked surfaces use two samples (colour and lightmap), with an optional glow sample. They disable specular. Their static result goes through `EMISSION`, so merely assigning a normal texture or Godot's `AO` output will not relight that result.

Classic applies `clamp(2*sqrt(baked), 0.25, 1.5)` independently to RGB; Contrast uses a shared peak-based shoulder. Classic lifts dark values and clips bright channels, which can flatten differences or change colour ratios. This is an artistic response, not proof of a colour-space bug. A faithful comparison must also account for Quake palette values, light compiler encoding, sRGB decoding and final Filmic output. Simply copying QuakeSpasm's multiplier into a different colour pipeline would not guarantee its appearance.

The existing Vulkan [25-map contact sheet](../test-results/lighting-ao-distribution/contact-contrast.jpg) shows substantial map-to-map brightness variation and prominent repetition/texture-scale differences. Those are targets for art and bake tuning before adding costly surface effects. The [source audit](MAP-TEXTURE-SOURCES.md) found no supplied PBR companion set in the project's Makkon/LibreQuake archives.

## Ranked implementation candidates

Costs below are engineering estimates relative to the present renderer, not measured milliseconds. “Negligible” means the same pass and sample count with little or no extra shader work; it does not mean zero implementation effort. Memory and covered pixels matter independently of draw count.

| Priority / technique | Expected visual impact | Expected standalone VR cost | Concrete approach and limits |
| --- | --- | --- | --- |
| 1. Calibrate colour/lightmap response | **High**, across every map: stronger depth, controlled highlights and readable shadows | **Negligible** if integrated into the current shader/tonemap | Evaluate a hue-preserving response and per-map exposure metadata against Classic/Contrast. Keep a readable shadow floor. Avoid a new fullscreen pass, automatic exposure pumping or arbitrary global darkening. |
| 2. Targeted bake improvements | **High** where lighting is flat or fixtures do not explain the light | **No added runtime work** if atlas dimensions stay fixed | Refine emitter placement, warm/cool separation, bounce and local minimum light; improve smooth shading on appropriate curved stone. Existing AO/bounce are already implemented. More supersampling mainly costs bake time, not more runtime texels. Do not increase AO indiscriminately. |
| 3. Offline texture/mipmap polish | **Medium–high** for texture stability and clarity in motion | **Negligible**, potentially lower bandwidth | Verify linear-light colour mip construction, transparent-edge padding and alpha coverage where needed. Keep mipmapped anisotropy; compare 2×/4× anisotropy on device rather than forcing maximum. Avoid negative LOD bias and sharpening that revive shimmer. Alpha-edge work mainly helps future/imported cutout surfaces. |
| 4. Map-specific skies and restrained depth/height fog | **High** for identity and distant depth, especially Vesper/Pressureworks | **Low**, when fog stays in the existing material pass | Load authored sky choices; use uniform/exponential or height fog without volumetrics, screen textures or overlapping fog cards. Match the sky horizon and preserve target contrast. Indoor regional fog needs surface/zone design; a camera-only zone toggle can produce incorrect cross-door views. Fog alone does not reduce rendering cost. |
| 5. Animated liquids, teleporters and texture frames | **Medium–high** local liveliness and source-map fidelity | **Low** for bounded UV math or one selected frame; extra memory for frames | The importer marks liquid textures but the ordinary material path does not implement their warp; generic Quake animation is also absent. Animate base and glow consistently, retain depth writing for opaque surfaces, and avoid screen refraction or whole-eye underwater distortion. Existing conveyor offsets are a useful starting point. |
| 6. Authored grime, wear and material variation | **Medium–high**, less repetition and more natural joins | **Negligible** when baked into artwork, lightmaps or existing vertex data | Vary approved tiles, scale and trims; add artist-controlled stains/moss and restrained vertex tint. Preserve source artwork and licence constraints. Extra overlays, texture blending and new material splits cost more than offline variants. |
| 7. Better authored glow masks | **Medium** around lamps, signs, runes and lava | **Low / existing cost** on surfaces already sampling glow | Current palette fullbrights work. Add deliberate masks only where useful; diffuse glow need not bloom or light nearby geometry at runtime. An alpha-packed scalar mask can remove a separate sample only when emission colour can be derived from base colour and alpha is otherwise unused. |
| 8. Smaller, better-packed/compressed static textures | **Indirect**: preserves fidelity while recovering performance headroom | **Potential improvement**, with format/artifact tradeoffs | Measure atlas occupancy, deduplicate shared textures and evaluate offline ASTC on Android and suitable desktop formats. A 4096² RGB atlas is 48 MiB of raw pixels (actual allocation may differ). Compression must be reviewed for colour banding and AO/lightmap bleeding; do not compress blindly or increase atlas count/draws to save bytes. |
| 9. Selective higher lightmap density | **Medium–high** on arches, stairs and close shadow boundaries | **Low shader cost; potentially large memory/cache cost** | First improve bake sampling at existing density. Finer luxel spacing requires importer/cache support; current UV reconstruction hardcodes 16 texture units. Halving spacing over the same surface area roughly quadruples texel count. Larger atlas dimensions alone do not add lighting detail. |
| 10. Offline cubemap reflections on a few surfaces | **Medium**: wet stone, metal and glass become distinct | **Low–medium**, extra cubemap sampling and storage on selected pixels | Bake fixed cubemaps offline; use broad, rough reflections and simple masks. No runtime probe captures. The current emission-based shader needs an explicit reflection contribution. Static reflections omit moving actors and can be spatially wrong away from their capture point. Avoid glossy coverage across the whole map. |
| 11. Directional lightmaps plus authored normal maps | **High locally**, actual relief responding to baked illumination | **Medium**, potentially high memory use | Add a direction atlas and normal texture: typically at least two extra samples on affected surfaces, plus tangent-space math. Split ambient/direct contributions carefully so existing irradiance is not multiplied by incidence twice. One average direction cannot represent all incoming light. Do a small Vesper stone/metal test, not a full-map conversion. |
| 12. Distance-faded detail texture | **Medium** close up; can conflict with painted art | **Low–medium**, usually one additional sample on covered surfaces | Limit to selected broad surfaces; fade before the pattern becomes subpixel. Prefer authored variations first. High-frequency noise can make VR less stable rather than more detailed. |
| 13. Bloom | **Low–medium**, atmospheric lamps but possible loss of clarity | **Medium–high** fullscreen bandwidth/filtering | Leave standalone default off. The existing emission already communicates bright surfaces. An optional PC-VR experiment should justify blur and stereo cost. |
| 14. Parallax/relief mapping, screen-space reflections/AO, volumetric fog | Potentially strong screenshots; variable benefit during play | **High or unpredictable** for the target | Defer. Iterative texture fetches, scene/depth copies, extra passes or temporal artifacts are poor first investments. SSR/SSAO/volumetric fog are not built-in Mobile features in the checked Godot matrix. Static AO is already present. |

Higher-fidelity normal mapping is not free merely because its light is baked. Conversely, better authored illumination can be nearly free at runtime because it changes the values already sampled.

The [ericw light documentation](https://ericw-tools.readthedocs.io/en/latest/light.html) exposes directional `.lux`/BSPX output and decoupled lightmap density, making rows 9 and 11 plausible. That does not establish compatibility with FPSloppa's current parser or guarantee all options exist in the installed v0.18 compiler; inspect that binary's help and validate coordinate conventions before implementation. Importing arbitrary BSPs must retain the present safe fallback when optional data is absent.

## VR decision and test sequence

Keep Mobile/Vulkan. Godot [recommends Mobile for standalone and desktop XR](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html); its feature matrix supports ordinary fog, tone mapping and MSAA there. Meta's [mobile GPU guidance](https://developers.meta.com/horizon/documentation/native/android/gpu-improved-algorithms/) and [impaired-algorithm discussion](https://developers.meta.com/horizon/documentation/native/android/gpu-impaired-algorithms/) explain why off-chip bandwidth and extra buffers deserve more attention than desktop FPS intuition. MSAA remains useful but is not universally free; [Meta's MSAA analysis](https://developers.meta.com/horizon/documentation/native/android/mobile-msaa-analysis/) reports workload-dependent costs. Those published timings are not FPSloppa measurements.

First prototype colour response and one map's sky/fog with toggles, then liquid/texture animation. Follow with offline art/bake refinements and compression checks. Preserve the existing AO baseline. Test directional shading/static reflections separately only after the inexpensive options are assessed.

Use reproducible A/B views in Vesper Abbey, Pressureworks, a long CTF route, one bright and one dark DM/KOTH map, and an imported BSP. Review both eyes while moving the head, not just still screenshots; include distant targets, grazing floors, cutouts and liquid boundaries. Performance tests must also use 4v4/6v6/8v8 loads and a thermally warmed headset, with runtime lighting held fixed between variants even though it is outside this study.

Record GPU/CPU p95 and p99 frame time, missed/reprojected frames, draw counts and texture memory at fixed resolution, refresh, MSAA and foveation settings. At 72/90/120 Hz, the whole frame lasts 13.89/11.11/8.33 ms; the application cannot spend all of that on new effects. As a proposed promotion gate, require no increase in missed frames and at most 0.2 ms p95 GPU regression for the combined first-stage low-cost features at the chosen target refresh, while retaining existing headroom. This is a test budget, not a prediction. Quest success does not replace Pico testing; PC-VR has separate headroom and stereo costs.

The earlier 25-map AO run found no extra draws/texture allocation and a median paired desktop Vulkan GPU delta of 0.0 ms, consistent with an unchanged shader. That supports the *bake-first mechanism*, not a performance guarantee for fog, normals or reflections. See [the existing AO receipt](validation/lighting-ao-distribution.json).
